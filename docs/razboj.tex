\begin{abstract}
A rasteriser reads a display list and writes pixels into memory.
Razboj, the minimal GPU of this document, is one: a unit whose process
is some two hundred and seventy lines of code, written as a sequence,
that walks a box one pixel a cycle, keeps three edge functions as it goes, and writes the pixels
that are inside the primitive as AXI bursts, a run of a row's pixels
at a time; the
framebuffer is a second unit, a memory behind the other end of the
link. The display list is in that memory too, and the rasteriser
reads it over the same link, so a program that writes the list is all
it takes to give Razboj work. Both are written in the lowered subset,
so both are netlists,
and the build simulates each netlist against the run that drew the
picture in this document, under \code{nvc} and under Verilator. The
rasteriser is also the first client of the AXI link that is hardware
rather than a testbench, and it is what that half of the link is for.
\end{abstract}

\section{The Display List}
\label{sec:g-list}

A display list is a little instruction set, and its four entries
carry different things. A clear carries a colour and nothing else. A
rectangle carries a box. A triangle carries three vertices, and a
shaded triangle carries a colour at each of them as well. That is
what an \code{enum} says in Rust, and it is what a program writes.
A colour is \code{0xAARRGGBB}: the alpha goes into the top byte of the
pixel, which the colour leaves free, so the framebuffer holds it for
whatever reads it next; nothing here does yet. A shaded triangle blends
red, green and blue, and its alpha is its first vertex's all over.

\gpupart{op.rs}{op}{The instruction set: \code{Op} as a program writes
it, \code{Kind} as the hardware reads it, and \code{Insn} as it goes
on the wire.}{lst:g-op}

\code{Insn} is one shape, as wide as the widest entry needs, because
every field a step of the rasteriser reads has to be at a fixed place:
the lowered subset slices a channel's word at constant offsets, and a
variable-width encoding would want a length field and a shifter in
front of everything else. A clear therefore leaves the box, the
vertices and the shading at zero, a rectangle leaves the vertices and
the shading at zero, and a flat triangle the shading; the kind says
which of them mean anything. That is a fixed-width
instruction word, and it costs what one costs: the widest entry sets
the width, and the narrow ones pay for it.

Between the two is an assembler, and it does what a host can do once
per primitive rather than once per pixel.

\gpupart{op.rs}{encode}{\code{Op::encode}: the assembler. It clips the
box to the screen, winds the triangle so that its inside is where
every edge function is non-negative, and drops an entry that would
draw nothing.}{lst:g-encode}

One more entry draws nothing and is not an instruction at all:
\code{Op::Scissor} sets a box that the entries after it are drawn
inside, until the next one. The rasteriser only ever walks an entry's
box, so clipping that box to the scissor box is the whole of the
scissor test, and the assembler does it as it clips to the screen,
once an entry. A clear under a scissor box is the one entry that
changes: it becomes a rectangle of that box, since the box the
rasteriser supplies for a clear is the screen. A box that holds the
screen is no box, and a box wholly off it draws nothing until the next.
Nothing in the hardware knows there is a scissor box.

The kind is read by the hardware in one place and decides three
things. A triangle, flat or shaded, is the entry whose edge functions
are tested; a shaded triangle is the entry whose colour is worked out
at each pixel; a clear is
the entry whose box the rasteriser supplies, from the screen size in
its own type, since a clear is the whole screen by definition and
there is nothing for the instruction to say. A rectangle is the plain
case, its box read and its edges ignored. These lines are the
whole of the decoder:

\begin{lstlisting}[frame=none,numbers=none]
let boxed = Bit::from(self.kind.get() != Kind::Tri)
    & Bit::from(self.kind.get() != Kind::Shaded);
let clearing = self.skind.get() == Kind::Clear;
let wx = mux(clearing, zero16, self.sx0.get().resize::<16>());
let shaded = self.kind.get() == Kind::Shaded;
let rgb = mux(shaded, shade, self.colour.get());
\end{lstlisting}

A wider instruction set would grow that decoder and not the walk,
which is the property worth having: a line, a circle or a sprite would
each add a kind and a way to say whether a pixel is inside, and the
one pixel a cycle, the three edge accumulators and the AXI writes
would stay as they are.

\section{The List in Memory}
\label{sec:g-mem}

\code{Insn} is how the list is held in a program and in a model.
In the memory it is words, and the format of those words is the one
thing software and hardware both have to agree on, so it is stated
once, in \code{gpu/razboj/src/dl.rs}.

\gpupart{dl.rs}{format}{The display list as a program writes it:
sixteen words an instruction, and no field across a word.}{lst:g-format}

An instruction takes sixteen words, so that the address of the
$i$th is the list's base plus $i$ shifted by six, a shift rather
than a multiply. No field crosses a word, so a program writes a field
with a shift and a mask and the rasteriser reads it with a slice at a
constant offset. Beside the list is one more word, the count. The
rasteriser reads the count until it is not zero, and then the list;
a program therefore writes the list first and the count last, and
writing the count is how it says the list is ready. The rasteriser
answers in the same word: when the list is drawn it writes the count
back to zero. Nothing else passes between the two.

So the rasteriser has a front end. It polls the count, fetches the
sixteen words of an instruction as one read burst of sixteen beats, latching
each field as its beat lands, draws the instruction, and fetches the
next; when
the count is used up the list is done, and Section~\ref{sec:g-lists}
says what follows. Every field is latched, the third vertex's
included, and the setup the walk needs takes three cycles after the
fetch; Section~\ref{sec:g-vivado} says why. One burst is
out at a time, because the front end has nothing to do until the
answer lands, so an entry costs one round trip of the link and then
a beat a cycle, where sixteen single reads cost sixteen round trips.
Every entry is fetched whole, so an entry that is not a shaded
triangle reads nine words of zeros, nine cycles it could skip. The
count is sixteen bits, so a list holds up to 65535 entries.

\section{List After List}
\label{sec:g-lists}

A picture that moves is a list a frame, so the rasteriser draws list
after list. It reads the count only while its \code{ring} input is
high. On the board a doorbell, the register that holds the count,
drives \code{ring} while the count is not zero, so an idle rasteriser
puts no reads on the bus (issue~\#985). Here \code{ring} is tied
high, and the count is polled back to back. When a list is drawn it waits until every write it made
has been answered, writes the count back to zero, and waits for that
write's answer too; then it polls the count again. A program waits
for the zero, writes the next list, and writes its count last, as it
did the first. \code{idle} says the same on a line: it rises once the
zero has been answered and falls when a count that is not zero is
read. Figure~\ref{fig:g-lists} is that hand-over.

Both waits are there for a memory that is not this one. Until every
pixel's write is answered, a program that saw the zero could read a
framebuffer the last pixels have not reached. And until the zero is
answered, a memory that let a read pass a write could answer the next
poll with the old count, and the list would be drawn twice.

\section{The List in Tiles}
\label{sec:g-tiles}

Razboj is to draw in tiles of 64 by 64 pixels, so that a depth test
and blending read and write block RAM beside the rasteriser and not
DDR3, which then sees one write a pixel a frame
(\code{docs/razboj-tiles.md}, issue~\#991). The first piece is on
the CPU, and it changes nothing in the hardware: sorting a list into
the tiles each entry touches, which is binning. It is a crate of its
own, \code{razboj\_tile} in \code{gpu/razboj/tile/lib.rs}, with no
standard library and no allocation, so that a program on the
core~\cite{vreteno} can bin its own lists with the code the tests
check.

A tile is a scissor box, so binning an entry is clipping its box to
each tile it touches, with the same clip the scissor box uses, which
moved into that crate for the purpose. A clear becomes a rectangle of
its tile, since a clear's box is always the whole screen. The edges
need nothing, since the rasteriser tests them against the same
vertices whatever the box. A shaded triangle's planes do: they start
at the box's first pixel, so a clipped entry's start is the whole
entry's stepped to the clipped box's first pixel, in the thirty-two
bits the walk's own adders wrap in.

\tilepart{entry}{An entry clipped to a tile: a clear becomes a
rectangle, and a shaded triangle's planes are stepped to the tile's
first pixel.}{lst:g-tile-entry}

A frame becomes a table of tiles, each a record of two words, and the
entries each tile takes, one tile after another, in the list's order.

\tilepart{format}{The tile table, stated once, in the crate a program
writes it with.}{lst:g-tile-format}

The tests draw each scene with the model twice, as a list and binned,
and the two pictures are the same pixel for pixel: the demonstration's
house across tile edges and corners, shaded triangles over many tiles
and off the screen, a clear and a triangle under a scissor box that
crosses tiles, scenes of pseudorandom entries, and the mesh of issue
988 laid over the tiles so that every tile edge is a mesh edge, which
still covers every pixel exactly once. A shaded triangle worked out
afresh inside each tile rounds each tile's start at a different place
and draws a different picture; one of the tests keeps that as the
reason the planes are stepped.

The rasteriser draws a tile table itself (issue~\#1255). A program
lays the table out where it would put a list, with the entries a fixed
two kilobytes past it, room for every tile's record, and rings the
count with bit 31 set, which says the count is the table's tiles. For
each tile the rasteriser reads its record and draws its entries as it
draws a list's, but into a tile buffer beside it, a bank of 4096
words, with a mark for each pixel written. Then it writes the tile out
a row at a time, each row one write burst of 64 beats. A beat's
strobes are on where a pixel was written and off where none was, so a
pixel no entry covered keeps what memory had, as it does from a flat
list, and the marks are cleared as they are read, which leaves the
bank empty for the next tile. The bank's reads land in a register a
cycle ahead of the beat, which is what makes it a block RAM. A flat
list, with the bit clear, is drawn as before, straight into memory, so
every program that rings a flat list draws what it drew.

Six scenes of rectangles, flat and shaded triangles and clears, over
tile edges and off the screen, drawn one over another, are the same in
tiles as flat, byte for byte, and \code{//docs:razboj\_tiles} replays
the rasteriser's netlist against a tiled run under both simulators. On
the board's model a tiled list, written into the DDR3 and rung, draws
what the model draws, and a word in a touched tile that no entry
covers keeps its value.

On the board's model, from the ring to the drawing done, a fill of
the screen's 640 by 480 takes 326973 cycles flat and 636144 in tiles,
and the icosahedron's first frame 452600 and 764607. In tiles a plain
fill is slower, and by design for now: with one bank the rasteriser
draws a tile and then writes it out, where flat it writes as it draws.
A second bank, so that a tile is drawn while the last goes out, and
the depth test, which a tile buffer answers without a read of DDR3,
are what the tiles are for (\code{docs/razboj-tiles.md}, section 7).

The depth test is the first of them (issue~\#992). An entry can test
depth: word 15 says whether it does, which of GL's eight comparisons it
makes and whether it writes its depth, and such an entry takes a second
slot right after it for its depth plane, a value and two steps with
twelve bits of fraction, so that sixteen bits of depth fit. Every other
entry takes one slot, so no list that does not test depth changes. In a
tile the rasteriser reads the plane's slot and steps it with the walk;
a pixel of such an entry reads the depth bank at its place, is compared
with what was there a cycle later, and a cycle after that, at the same
address, is kept if it passed, and writes its own depth if the entry
says so. Each depth
written sets a mark, which the write-out clears, and a depth not marked
reads as the farthest, so each tile starts far while the depth bank is
read and written at one address only, which keeps it a block RAM. Depth lives only in the tile buffer, so a flat list has none: its
depth entries draw as if depth were off, and a program that wants depth
rings a tile table. Under every comparison, scenes of overlapping
triangles are drawn in tiles as the model draws them, byte for byte,
\code{//docs:razboj\_depth} replays the netlist's depth test under both
simulators, and on the board's model two triangles that cross in depth
are each seen where they are nearer.

\section{The Rasteriser}
\label{sec:g-raster}

An edge function is linear. For the edge from $a$ to $b$,
\[ e(x, y) = (b_x - a_x)(y - a_y) - (b_y - a_y)(x - a_x), \]
which is zero on the edge, positive on one side and negative on the
other. A vertex is in sixteenths of a pixel, and the function is taken
at each pixel's centre, so a triangle can lie between pixels and
cover the ones whose centres it covers. Stepping one pixel to the
right adds sixteen times $-(b_y - a_y)$ and stepping one row down
adds sixteen times $(b_x - a_x)$, whatever the pixel. So the
rasteriser keeps, for each of the three edges, its value at the
current pixel, its value at the start of the current row, and those
two steps.

A centre exactly on an edge belongs to one triangle only: the one for
which the edge is a top or a left edge, where inside lies to the
right, or below a level edge. The setup subtracts one from the
starting value of every other edge, so that a centre on it fails the
sign test there, and of two triangles sharing an edge exactly one
draws the pixels on it. A mesh of triangles over the screen draws
every pixel once and misses none, which a test checks against the
model and against the count of pixels written.

A shaded triangle's colour is linear across it in the same way, one
plane for each of red, green and blue, and so each channel is kept
exactly as an edge is: its value at the current pixel and at the start
of the current row, and its two steps, with sixteen bits of fraction
below the byte the pixel takes. The host works a plane out once per
triangle, from the three vertices and their colours, as its value at
the centre of the box's first pixel and what it gains a pixel to the
right and a row down, and the rasteriser loads those as they land and
does no setup for them at all. A channel below nought is written as
nought and one of 256 or more as 255, which a pixel at the very edge
of the triangle can reach by the rounding of the steps; the plane
itself does not wrap inside the triangle, since the value there is
between two of the vertices' colours.

\gpupart{raster.rs}{state}{The rasteriser's state.}{lst:g-state}

The only multiplications are the six of the setup, done side by side
in the second of the three cycles the setup takes; the per-pixel work
is three adds and three sign tests, and three adds more for a shaded
triangle's channels. The arithmetic is thirty-two bits of two's complement, which
is wide enough for every product of two differences of vertices in
the range an entry may use: 1024 pixels either side of the origin, in
sixteenths. It was sixteen bits first, and a
pseudorandom scene with a vertex off the screen found the overflow
within a dozen tries, which is the argument for the soak test rather
than for the directed ones.

\gpupart{raster.rs}{run}{The rasteriser, two processes.}{lst:g-run}

The rasteriser is two processes. The first takes the link's answers
every cycle, says whether the pixel under the walk is in the
primitive, and counts what is in flight. The second is the front end
written as the sequence it is: poll the count until the list is
ready, then for each instruction fetch its sixteen words, as one read
burst with each beat latched as it lands, and walk its box, every row and
every column a counted loop, a pixel a turn; when the list is drawn
it writes the count back to zero and polls again. The lowering numbers the waits into a state
register of its own and gives each counted loop a counter, so the
netlist keeps what the hand-numbered machine before it kept in a
phase and a step without the source naming either.

The walk is one pixel per turn: the column advances and each edge
and channel takes its column step, and at the end of a row the column
goes back to the first and each edge and channel is reloaded from its
row value plus its row step, with one cycle between rows for the box to read back. A
pixel is written only when the link has room for the burst and its
beat, and the turn holds until then, so backpressure from the bus
stops the rasteriser rather than losing pixels.

\section{Writing Over AXI}
\label{sec:g-axi}

The rasteriser is an AXI host, and it is a host written as hardware.
The \code{Host} end of a link~\cite{axi} is a simulation-side
convenience, with an inbox, a table of answers and futures to await;
none of that lowers, and none of it needs to. What is underneath is
channels, and a client that is a unit holds those channel ends
itself: the issue channel and the write beats going out, the grant,
the write responses and the release coming back. \code{axi\_units}
hands them out under the names \code{HostClient} and
\code{PerClient}, and that is the whole of the difference between a
client that is a testbench and a client that is hardware.

A run of a row's pixels is one burst (issue 987). The first pixel of
the primitive that the walk meets with no burst under way starts one,
as long as the pixels left in the box's row, at most sixteen and short
of the next 4~KiB page, and its issue and first beat go out in the same
cycle; each pixel after it in the burst sends a beat, its strobes on
where the pixel is inside the primitive and off where it is not. So
the write data channel stays in the order the address channel is in,
which is what AXI4 asks of a write. A triangle's pixels in a row are
one run, since it is convex, so a burst wastes beats only past the
run's end, and a clear or a rectangle writes nothing but whole bursts.
On the board's model, with nothing else on the bus, a fill of the
screen's 640 by 480 now ends at cycle 327426, about one a pixel; a
burst a pixel ended it at 1229346, four a pixel.
The
identifier the tracker granted is not needed, since a write's answer
matters only as a count and the front end has one read out at a time,
so it is taken and dropped. An identifier is handed back on
\code{release} as the answer arrives: a write's with its response, a
read's with its last beat. That is what keeps four transactions in flight
and no more. A write's response is taken before a read's beat in the
cycle both arrive, since only one identifier goes back a cycle, and
the read waits a cycle for it.

\section{The Framebuffer}
\label{sec:g-fb}

The framebuffer is the peripheral end of the same link: a memory of
one word per pixel, answering bursts of any length. A beat writes only
the bytes its strobes name, so the beats of a burst that fall outside
the primitive write nothing, and a write is answered once, with its
last beat.

\gpupart{fb.rs}{run}{The framebuffer.}{lst:g-fb}

It holds the display list as well as the pixels, above them. A read,
which is only ever the rasteriser fetching that list, is answered
from the memory in the cycle the request is taken.
A write is held until its beat arrives, because AXI4 puts no
identifier on the write data channel, so the beat belongs to the
oldest address phase and there is nothing to match it by but order.
One write is held at a time, which is why the demonstration takes
about four cycles a pixel rather than one; a framebuffer that took a
request and its beat together in the cycle both were offered would be
the first thing to improve.

\section{The Netlists}
\label{sec:g-netlist}

Both units lower. The traced run is sixteen by sixteen pixels, small
enough that a testbench generated from its trace replays in a moment,
and the build checks both netlists against it at their ports, as VHDL
under \code{nvc} and as Verilog under Verilator. Listing~\ref{lst:g-out}
is what that run printed.

The framebuffer's netlist is told what its memory starts with, the
list and its count, which \code{Mem::with} gave the run and which the
lowering cannot see; without it the simulated module reads zeroes
where the run read the list. The rasteriser is also the first unit
checked this way that does something in its first cycle, since it
goes looking for the count at once, and the testbench generator
starts a channel's \code{ready} high for that reason: an empty
channel has room, and the first cycle has no sample in the trace to
say so.

\lstinputlisting[style=ascii,caption={What \code{//gpu/razboj:trace} printed
when the build ran it: the same three kinds of entry on a screen
small enough to print.},label={lst:g-out}]{out_razboj.txt}

Three names had to be changed to lower. A register called \code{next}
gives VHDL a signal called \code{next}, which it reserves; a register
called \code{tri} and a wire called \code{inside} give Verilog two of
its own reserved words. The lowering emits a name as it is written,
and it did not then reject the reserved words of its targets, so the
failure was an analysis error in a generated file rather than an error
at the point the name was chosen. It now refuses such a name where the
name is declared. The registers here are \code{edged} and the wire is
\code{hit}.

A fourth mistake is worth stating because the lowering did not catch
it either: a \code{let} that computes, and takes the name of a
register, produces two declarations of one signal. That is now refused
too, at the \code{let}, once the unit's \code{lowered} is compiled.
The locals in the rasteriser are
\code{px}, \code{py} and \code{held} for that reason, where \code{x},
\code{y} and \code{waiting} would read better.

\section{Through Vivado}
\label{sec:g-vivado}

The rasteriser has been synthesised, out of context, with the board's
parameters: thirty-two-bit addresses, two-bit identifiers, and a 640
by 480 screen in rows of 1024 pixels (\code{//gpu/razboj:razboj\_synth}).
Placed and routed (\code{:razboj\_pnr}), it takes 1683 LUTs, 1323
registers and 18 DSP blocks, and no block RAM: about one per cent of
the part's logic. The multiplications of the setup are the DSP
blocks. The shading added 373 LUTs and 386 registers to the flat
rasteriser, and no DSP block, since the host does its division and the
rasteriser only adds; its twelve 32-bit accumulators are 384 of those
registers. The alpha added 14 LUTs and 9 registers more, its byte and
the fetch counter's fifth bit; the scissor box added nothing, since it
is the assembler's.

It meets the 100\,MHz the board's bus runs at, with a worst setup
slack of $+1.193$\,ns and hold met. It did not at first. The setup
of a triangle computed each edge's value at the box's first pixel, two
32-bit products and a subtraction, in the one cycle the entry's last
word landed, a path of 11.66\,ns, and the slack was $-1.660$\,ns
(issue 1034). The setup now takes three cycles, the differences, then
the six products side by side, then their sums, and the worst path is
one multiplication, 8.20\,ns. That costs three cycles an entry: the
demonstration's eight entries take 24 cycles more, about 0.15 per
cent.

\section{What It Is Not}
\label{sec:g-not}

It is minimal, and the ways in which it is minimal are worth naming.
There is one pixel per cycle and no more, two for a pixel that tests
depth; depth only in a tiled list, so a flat one draws its primitives
in the order the display list gives them; no
interpolation but of colour, and that in the screen's plane, without
the correction for perspective a texture would need; an alpha
written and never read, so nothing is blended; no texture; no
clipping
of geometry, only of the box; and one burst out at a time, so each
entry's fetch waits a round trip of the link. Every one of those is a
thing to add on top of what is here rather than a thing to work
around.

The shading is split the same way. The host works out each plane,
which takes a division, and the hardware only steps it. A rasteriser
that took the three colours and did the division itself would carry
three words where it now carries nine, and it would change the setup
and nothing after it: the walk would step the same accumulators by the
same steps, wherever those came from (issue 989).

A CPU writing the display list is the step the bus was for, and it is
taken in the network document~\cite{noc}: the core~\cite{vreteno}
works out an icosahedron and writes it into a memory Razboj shares,
two hops away on a lattice.
