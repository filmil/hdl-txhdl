\section{The Rule}

TxHDL is a hardware description language that is a Rust library. It
was built by deleting every construct Rust already provides. A
transaction is a \code{struct}; a unit is a \code{struct} that
implements \code{Unit}; a pipeline is an \code{async fn}; a
configuration is a trait; a clock is a type, and so is the reset
beside it: every module the netlist writes has one, every lowered
child is joined to its parent's, and no unit declares a port for it,
which a reset port would have asked of about 127 \code{.run} call
sites; under it a register goes back to what it held before the
first edge and a channel empties. \code{rustc} is the
parser, and its type checker is the design rule checker: two drivers
on a wire are a move error, a clock domain crossed without a
\code{Crossing} is a type error, and a cycle counted in combinational
logic is impossible because a plain \code{fn} has no \code{.await} to
write in.

What is left is a unit, and a unit is a netlist. Listing~\ref{lst:w-unit}
is one whole: a counter that ticks once in eight cycles while
enabled. \code{\#[lower]} gives it a Verilog module and a VHDL entity
beside the Rust, and the build simulates both against the Rust run's
own trace, every time.

\section{Vreteno, a Core}

Vreteno is an RV32IMC core: fetch, execute and writeback, with the
multiply and divide as a sequence, the machine control registers, the
timer and the external interrupt. It is checked against a reference
model of the instruction set written as a program, in lockstep, every
cycle: the program counter, the thirty-one registers and the control
registers must agree after each retirement, on a demonstration
program and on sixty-four random ones.

It runs on hardware. The netlist goes through a hermetic Vivado onto
an Alinx AX7A200, and the board says on its serial port what the
simulation says it will: \code{OK}, and then whatever is typed at it,
echoed. The same netlist also goes onto an open 45~nm standard cell
library, through Yosys and OpenROAD, both fetched by checksum: a die
\asicdie~$\mu$m square that meets \asicfreq~MHz and routes with
\asicdrc{} violations. That is a layout and not a tapeout, and
\code{//docs:tapeout} says what a tapeout would still want.

Its bus is AXI4, and every device behind it is an AXI peripheral,
with the router deciding by address which one a burst reaches. On the
board that includes a gigabyte of DDR3, through a controller brought
in as a foreign module: the first thing here the language wires
rather than writes.

\section{The AXI Link}

A channel carries one transaction. AXI is five channels that only
mean something together, so the library provides the link rather than
the channels: \code{axi()} makes every channel of it at once and
hands back two ends, the way \code{chan()} hands back a sender and a
receiver.

A host client issues a burst and awaits its answer, in any order. A
peripheral client accepts a whole transaction and answers it from
whatever process holds it. Neither names a channel, counts a beat or
writes an identifier. Two trackers between the ends do the protocol,
and a router goes between them without changing client code.

\section{A Network}

A router puts several peripherals behind one host. For several of
both, there is a lattice of nodes, each with a two-way link to its
four neighbours and a fifth, the exit, where a bridge with AXI on one
side and packets on the other attaches. Every link is two virtual
channels, one for requests and one for responses, which is what keeps
a full path of requests from holding up the answers that would empty
it. Routing is dimension order, which on a lattice needs nothing else
said to be free of deadlock.

Neither end knows the network is there. A host issues a burst and
awaits its answer as it would on a link; a peripheral accepts a
transaction and answers it as it would. What the network adds is the
renaming: an identifier belongs to the host that made it, so a
peripheral bridge gives every request one of its own and remembers
the node and the identifier to answer under.

Vreteno, Razboj, a memory and a serial port sit on the four corners of a
two by two lattice, as Fig.~\ref{fig:s-noc} shows, and run together: the core works out an
icosahedron and writes it into the memory they share as a display
list, and the rasteriser, which has been watching for it, reads the
list and draws it there. Drawing across the lattice takes Razboj a
little over twice as long as on a link, which is what never waiting
for an answer costs on a network that moves one packet a node a cycle.

\section{Parts}

A part is hardware the language provides, written in its own lowerable
subset and checked as every unit is, so nothing in the library is a
primitive the compiler knows and the user cannot read. A reservation station gathers the operands
of an operation that arrive on separate channels, out of order, and
fires when the last of them has.

It has grown outwards from the bus since: an Ethernet MAC, HDMI video
with the I2C that configures the chip and a general I2C master beside
it, general purpose pins, an SPI master, a system control block that
says which design is running and why it last restarted, a watchdog
that restarts it when software stops saying it is there, and a bridge
from AXI to Wishbone, which lets a controller written elsewhere be a
peripheral here.

The bus itself has both halves now. A router puts several peripherals
behind one host and decides on the address; an arbiter puts several
hosts on one peripheral link and decides whose turn it is, tagging
each host's identifier so the answers find their way home. Until there
was an arbiter, the core was the only unit here that could be a host.

\section{From an Empty Directory}

A reader with nothing installed but Bazelisk writes four files, and
the fourth is a blinky that builds, runs, and lowers to Verilog and
VHDL. That workspace is kept in the tree and built as a check, so the
tutorial cannot rot: it depends on the project the way anyone else
would, through the public mirror. The build fetches every toolchain in
Table~\ref{tab:w-tools} itself, by checksum or from source. Nothing is
installed by hand, on a workstation or in CI.

\section{How It Is Checked}

Nothing here is checked by reading it. Every example is a program the
build runs, and its output is included in a document from the run, so
a document cannot drift from the code. Every simulated unit of
Table~\ref{tab:w-units} runs twice more, as VHDL under \code{nvc} and
as Verilog under Verilator, against the trace the Rust run wrote, at
its ports. \code{bazel test //...} runs three hundred and twenty-two
targets, of
which a hundred and ninety-two are netlists under both simulators; the rest are the
core's model and
programs, the board's own run, Razboj, the parts, the SoC's run, and
the tools. Seven more are tagged manual: the board and its DDR3 under
Vivado's simulator, the DDR3 controller alone and AMD's own test of
it under the same, the PCIe endpoint on its own and against a root
port under the same, the AXI link's fuzzing over many seeds, which
the nightly run does, and the check that every component has a
datasheet, which a sweep of the documents runs. Every claim about what
Rust accepts was compiled first, as a probe kept in the tree,
including the ones whose answer was no.

\section{What Is Not Done}

A wire may take a name other than the one its \code{let} is written
with, and the netlist says which: it carries a line per renamed
\code{let}. No \code{let} Rust accepts is refused any more. The core
fetches from the bus above its boot memory, so it runs a program it
was not built with, and the boot memory is on the bus too, readable
and not writable; but a fetch that leaves the core stalls the
pipeline until the word is back. A wrapping burst does not cross the
network on chip; it is refused rather than carried, and an
incrementing one crosses as that many writes of one beat. Razboj has no depth buffer, no
interpolation and no texture. Each is an issue on the repository rather
than a paragraph here.
